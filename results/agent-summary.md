# Agent usage log

One row per `pw code` agent session, kept so that the run-to-run variability
in turns and tokens for the same agent, test and model can be tracked over
many test runs. This is a log, not a benchmark.

How to maintain this file:

- APPEND one row after every agent session in a test, including failed or
  abandoned attempts. Never edit or delete earlier rows; a correction gets a
  new row that says what it corrects.
- Exactly 11 columns, in this order:
  agent | test | llm | turns | tokens | prompt | completion | cached | result | outcome | mode.
  - `agent`: the exact pw code agent name (`site-runner`, `site-runner-mcp`,
    `evaluator`, `compare-agents`, ...), or `default` for the main session.
  - `test`: `YYYY-MM-DD` and a short descriptor, e.g. the target, grid,
    attempt number and run id.
  - `llm`: the short model name, e.g. `gpt-oss-120b`.
  - `turns`: `iterations` from `pw code -p ... -o json`, as a bare integer.
  - `tokens`: `usage.total_tokens` from the same JSON, as a bare integer
    (no commas, no `k`).
  - `prompt`, `completion`: the same total split into `prompt_tokens` and
    `completion_tokens`, summed over the session's requests (the session
    transcript's `usage` records, or `usage` in the hook digest);
    prompt + completion = tokens. Prompt processing and generation run at
    very different rates, so the split matters for timing.
  - `cached`: the sum of `prompt_tokens_details.cached_tokens`, the part of
    `prompt` the server reused from its prefix cache instead of processing
    again. `-` when the server does not report it (the vLLM gpt-oss endpoints
    do not), which does not mean nothing was cached.
  - Use `-` for any value that can no longer be recovered. Rows before
    2026-10-27 have `-` in prompt, completion and cached: those columns were
    added on 2026-10-30, and the transcripts for older sessions are gone.
  - `result`: a short outcome, e.g. the scheduler job id and its final state.
    Start it with FAILED, PARTIAL, CANCELLED or WRONG when that applies.
  - `outcome`: `PASS`, `FAIL` or `-`, judged from the session's own job
    (added 2026-11-09; earlier rows were classified from their `result` text):
    - `PASS`: the session did the job it was given, without human help, and
      reported it truthfully. An evaluator that correctly returns a FAIL
      verdict is a PASS (the application failed, the agent did not). Minor
      procedure slips that do not change the outcome still PASS: a recovered
      denial, a skipped or taken id, a scratch file left behind, an
      out-of-scope read.
    - `FAIL`: the agent did not get the job done or reported it wrongly: no
      job, an invalid or mislabelled run, a false or invented report, missing
      or unrequested work, wrong delegation (wrong agent type, background
      when it should wait, delegating to itself), stopping early, needing a
      human nudge to continue, an empty turn, or a write-up with wrong or
      omitted findings.
    - `-` (not counted): correction rows (their tokens replace the corrected
      row's); failures caused by the cluster, the configuration or our own
      software rather than the agent (node faults, an unpushed commit, a tool
      false positive, missing toolchains, a host offline); sessions that were
      not a run (a cancel request); sessions the user cancelled; sessions
      whose agent is unknown.
    Pass rates are per agent and llm: PASS / (PASS + FAIL).
  - `mode`: how the session that ran this agent was started (added
    2026-11-11). A delegated agent takes the mode of the session it ran in.
    - `interactive`: a `pw code` session where a human types prompts.
    - `one-prompt`: a single prompt given on the command line, `pw code -p`
      (with or without `--agent`). Older rows call this "one-shot" in `test`.
    - `-`: not known for certain. Fill a mode in only when it is certain,
      never from a guess; pw records no mode in the session itself.
      Backfilled rows got a mode only where the row's own text stated it (or
      it belongs to a session whose row did).
- Never put a `|` character inside a cell.

Querying. A plain `grep site-runner` also matches `site-runner-mcp`, so anchor
on the agent column:

    grep '^| site-runner |' results/agent-summary.md
    grep '^| site-runner-mcp |' results/agent-summary.md | awk -F' *[|] *' '{print $5, $6}'   # turns tokens
    awk -F' *[|] *' '$2=="site-runner-mcp" && $4=="gpt-oss-120b" {n++; t+=$6} END {print n, t/n}' results/agent-summary.md
    awk -F' *[|] *' '$2=="site-runner-mcp" && $7!="-" {print $7, $8, $9}' results/agent-summary.md   # prompt completion cached

    awk -F' *[|] *' '$2=="site-runner-mcp" && $4=="gpt-oss-20b" && $11!="-" {n++; p+=($11=="PASS")} END {print p "/" n}' results/agent-summary.md   # pass rate
    awk -F' *[|] *' '$2=="orchestrator-mcp" && $11!="-" && $12!="-" {n[$12]++; p[$12]+=($11=="PASS")} END {for (m in n) print m, p[m] "/" n[m]}' results/agent-summary.md   # pass rate by mode

With `-F' *[|] *'` the fields are $2 agent, $3 test, $4 llm, $5 turns,
$6 tokens, $7 prompt, $8 completion, $9 cached, $10 result, $11 outcome, $12 mode.
